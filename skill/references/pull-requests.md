# Pull requests

Read when `FACTORY.md` has a `## Pull requests` section. Ticket work is then committed on a ticket branch, pushed, and reaches the integration branch only by merging its pull request. The section names the branches, the standing permissions and the forge's commands; run those. Assigning, peer review and the task record stay as in [leading.md](leading.md).

- **Branch:** one ticket has one branch, one developer writing and one pull request. Split a ticket that needs two writers into two tickets first. Fetch and fast-forward the integration branch in the main checkout, then create the ticket branch with `git switch -c <branch> --no-track <base>` to avoid an upstream config write.
- **Shared checkout:** with a clean tree and nobody writing, create the ticket branch in the main checkout before you assign. Members leave changes uncommitted; after the reviewer approves, commit on the ticket branch. One ticket at a time: the next starts when this pull request is merged, or the user says to go on.
- **Worktrees:** the main checkout stays on the integration branch. While the developer is not writing, give it a new branch for the ticket: set `worktree = "<user>/<ticket>"` in `factory.toml`, run `factory.py check`, then `factory.py down NAME` and `factory.py up NAME`. If the saved conversation cannot resume, `up` starts a new one and says so. Never reuse a branch whose pull request was merged. You and @pm stay in the main checkout. Do not mix the modes: no member has a worktree while the main checkout is on a ticket branch.
- **Git config lock.** If Git cannot lock the config, check the current branch and worktree status before retrying. A running Claude Code sandbox can hold `config.lock` in Git's common directory. Members report the error and status to the operator and leave the lock alone. Only the operator removes a confirmed stale lock after checking for active Git writers and sandbox mounts.
- **Permission:** the section gives standing permission in two lines: one to push ticket branches and open or update pull requests, one to merge. Without the line, ask the user at that action; their answer covers that action only.
- **Remote:** only you write to it. After the reviewer approves, push the ticket branch and open its pull request, or let the push update the one that exists; have the tracker owner link it on the ticket. After an unclear result from a push, an open or a merge, read the remote branch and the pull request before you retry, so nothing is made twice. Never force-push, and delete no branch unasked.
- **Checks:** run one bounded CI wait per pushed head, with a time limit that fits your harness. If it ends while checks are pending, run it again. If none is listed yet, pause first, longer each time. Stop and report errors such as sign-in failure or rate limits. Read the forge to reconcile a retry, just before merging and to confirm a merge. When checks finish, ask @reviewer for a readiness verdict on that head.
- **Ready** means, all on the pull request's current head commit: the reviewer approved that commit; every check the forge requires has passed, and when it requires none, every check has; no verified finding is open, whether from a failed optional check, an automated report or a thread; it can be merged. No checks listed is not ready, unless the section says the project has no CI and the forge requires none. A new commit voids all of it. The team's approval is not the forge's review approval: when the forge wants one from another person, report blocked and never bypass.
- **Stale base:** a pull request can be mergeable, with green checks, on a base that has since moved. Before you ask for a readiness verdict and again just before a merge, fetch, list the pull request's files with `git diff --name-only origin/<base>...origin/<branch>`, and run `git diff --name-only origin/<branch>...origin/<base> -- <those files>`. Any output means the integration branch changed a file the pull request changes: update the branch as under Conflicts. With no output, leave the branch as is.
- **Merge:** ready is a report, not permission. With permission, read the state once more and squash-merge that exact head: never a merge commit or a rebase merge, and if the forge does not allow a squash merge, report blocked. A queued merge is not merged: keep the ticket open and check again with a wait like the one for checks, or report that you wait on the forge. Confirm the merge on the forge, also when the user merged; then switch the main checkout to the integration branch, fast-forward it from the remote and have the ticket closed. Never merge a ticket branch locally.
- **Conflicts:** merge the integration branch into the ticket branch (the developer in a worktree, you in the shared checkout); never rebase. The new head needs new checks and a new approval.
