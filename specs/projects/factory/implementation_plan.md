# Implementation Plan: Factory v2

Each phase is one ticket on the board, built on its own branch, reviewed (fast lane plus codegenie) and merged through the `FACTORY.md` workflow. CI stays green on every phase: each phase deletes the v1 code and tests it replaces and updates the skill text that describes what it changed. Each phase follows the pairing in `FACTORY.md`'s Workflow: one architect plans `phase_plans/phase_N.md` and one other reviews it, one lead dev writes and one other follows each commit, the planning architect gives the final design review, and @reviewer gives the verdict. Phases 4 and 5a are built in parallel: 5a's live checks, adapters and lifecycle work proceed alongside 4, and 4 merges first for the integrated `up`, `status`, `say` and keeper calls. Phase 7's skill text may start early. Details live in the spec and architecture; this list is the order.

## Phases

- [ ] Phase 1: Early live checks. LC-1, LC-9 and LC-10 (architecture.md §10), plus LC-13: driving rodeo from a second `hc` core (started without `HC_TERMINAL_ID` or with a test-only `allow_nested`), typing into it with `hc keys` and reading its screen with `hc read`; on a separate `hc` session viewed in rodeo, with the small framed-attach client they need; record `tests/hc_fixtures.json` from the real core. Apply each fallback in the architecture before dependent code is written.
- [ ] Phase 2: Foundation. `hc` client (hc_client.md), shared constants, config with the three new optional keys, the fake `hc` and the fake OSC 7501 agent with contract tests against `hc_fixtures.json`; CI runs the suite (with a pinned `hc` if LC-9 allows). v1 back-port on the `v1` branch: accept and ignore the new `factory.toml` keys.
- [ ] Phase 3: Message log. `Log`, `Box`, append and commit, full validation and `log.check`, damage handling, outcomes, message files, and the reader `inbox_rows` (message_log.md, spec §8.6–8.7), with the fault tests. v1's commands are untouched: each phase removes what it replaces once its last caller moves, so `Inbox` stays until Phase 4.
- [ ] Phase 4: Keeper delivery and `say`. `decide`, per-recipient delivery and send-result mapping, `say`, `ensure_keeper`, heartbeat and single instance, the pane log (keeper.md §1–4, §8); crash and restart tests. Switches the `inbox` command to the v2 log together with `say`, its first writer, and moves the messaging parts of `status` and `up` in the same change: pending counts come from the v2 `Box` and point to `factory.py inbox --for <operator>`, with no cold-start unread hint and no `wait` instruction (their pane and launch parts stay for 5a). Removes v1's `wait`, old `say`, `Inbox` and `InboxDamage`; updates the member prompt's sending paragraph. No migration, dual reader or new flag: v1's inbox files stay byte-for-byte and are read with the retained v1 build in the original herdr session, documented as `python3 <v1-checkout>/skill/scripts/factory.py wait --cwd <original-checkout> --timeout 0` (unread, not acknowledged) and `python3 <v1-checkout>/skill/scripts/factory.py inbox 100 --cwd <original-checkout>` (acknowledged history). Acceptance includes a seeded test: an unread v1 ID and a different pending v2 ID; `status` and `up` show no legacy count or `wait` instruction, both v1 files stay byte-identical, and the v1 reader still prints the old ID.
- [ ] Phase 5a: Launch and team commands. Remaining live checks LC-2 to LC-8, LC-11, LC-12 first. Harness adapters and session capture (`session_env`, launch flags, resume), readiness and startup dialogs, labels, `check_operator`, and `up`, `down`, `status`, `check` with members running without panes (launch_layout.md, cli_skill.md). Removes `herdr()`, `Team` and v1's launch; updates the command table.
- [ ] Phase 5b: Layout and recovery. The `herdr-app` doc with compare-and-set, the team tab and keeper pane, placement labels, `brief` and `not ready` recovery, leftover message files, adoption by a new operator. From here on every phase ends with a rodeo smoke test (separate session, `up`, screen check, a message, a typed draft). It ends with a simplification pass: cut duplication and dead paths across `factory.py` without dropping specified behaviour or tests, and re-measure the size in architecture.md §4.
- [ ] Phase 6: Notes and autonomy. Member notes by observed episode, the team-quiet rule, the ready check, re-exec on version change and the pane title (keeper.md §5–7), with controlled-clock tests for every keeper row of spec §8a.3.
- [ ] Phase 7: Skill text. `leading.md`, the setup and recovery references, roles, templates (including the workflow in the `FACTORY.md` template), README and docs; installed-copy and docs checks.
- [ ] Phase 8: Qualification, first set. Spec §10 cases 1–10 with Claude Code and Codex as operator and all six harnesses as members, plus the cross-team cases; results recorded with versions.
- [ ] Phase 9: End-to-end autonomy. The local run (bare remote, file tracker, injected faults), then the private `pkieltyka/factory-test` run with its board, pull requests and CI; the empty-board run.
- [ ] Phase 10: Qualification, second set, and release. pi, omp, OpenCode and agy as operator; fix what they find; tag v2, and point skills-sync back at `master`.
